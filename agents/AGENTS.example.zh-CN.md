# 代理指令

本文件定义了使用本仓库的AI代理所采用的可复用操作规则。

在适配到您自己的环境之前，请先将其复制到`AGENTS.md`中。

<a id="core-rules"></a>
## 核心规则

1. 在采取行动前，必须先阅读相关的源文件。
2. 在进行实质性变更前，需明确成功标准、必须保持不变的内容以及所需的检查项。
3. 将提供的知识文件视为用户特定信息的权威来源。
4. 不得自行发明技能、经验、项目成果、实现细节或偏好。
5. 必须清晰地区分以下内容：
   - 已验证的事实；
   - 分析；
   - 建议；
   - 信息缺失。
6. 在研究当前信息时，优先使用原始资料。
7. 对于时效性较强的陈述，必须保留原始链接或参考信息。
8. 在修复问题前，必须先诊断失败：重现或追溯失败现象，确定其根本原因，然后修改负责的层级。
9. 优先选择满足已验证需求的最小实现方案，避免使用推测性抽象和新增依赖。
10. 除非任务明确要求，否则不得修改稳定知识文件。
11. 将生成的报告与权威来源文件分开保存。
12. 在更新文档时，应保留现有内容中的有用部分。
13. 优先采用最小差异更新，而非大规模重写。
14. 绝不能在公开输出中暴露机密信息、个人数据、私有路径或私有上下文。
15. 当无法验证某项主张时，应说明其局限性，而不是进行猜测。
16. 在相关情况下，必须明确区分已实现、已测试、已验证、实验性、计划中、已放弃和已被替代的工作内容。
17. 在相关测试、静态检查、构建或烟测试运行之前，不得声称已完成。

<a id="evidence-policy"></a>
## 证据政策

只有当存在具体证据时，一项技能、功能或成果才被视为支持，例如：

- 源代码；
- 仓库文档；
- 测试用例；
- 基准输出；
- 项目报告；
- 课程作业；
- 专业经验；
- 可复现的命令；
- 外部可验证的来源。

仅凭文件中出现的技术名称本身，并不足以证明具备相应能力。

缺少技能证据意味着‘未记录’，而非证明该人员不具备该技能。

<a id="file-safety"></a>
## 文件安全

以下位置默认为私有：

```text
AGENTS.md
local/
private/
```

除非明确请求且经过匿名化审查，否则不得将这些位置的内容移动到公开文件中。

当从私有来源推导出公开仓库或文档时，应提取可复用的模式，而非复制源内容。必须审查生成的差异，以确保不包含个人数据、凭证、绝对路径或私有项目细节。

<a id="career-workflow"></a>
## 职业工作流程

在进行职业研究前，请先阅读：

```text
local/career-profile.md
```

对于每一个机会：

- 确认其当前是否可访问；
- 验证其是否匹配请求的合同类型；
- 验证地理兼容性；
- 验证预期的学术层次；
- 提取重要的技术与非技术要求；
- 仅将要求与支持的候选证据进行对比；
- 识别最强支持的项目；
- 识别缺失或薄弱的证据；
- 避免仅仅为了增加结果数量而包含弱匹配项。

使用：

```text
templates/internship-research-report.md
```

用于输出结构。

<a id="project-workflow"></a>
## 项目工作流

在分析项目时：

- 在依赖文档之前，检查其实现细节；
- 区分当前实现与路线图项目；
- 区分活跃方法与已废弃的实验；
- 不要将未实际使用的技术归因于项目；
- 保持项目状态以证据为基础；
- 优先使用仓库证据而非营销用语。

<a id="knowledge-workflow"></a>
## 知识工作流

在更新知识库时：

- 提取持久的知识；
- 避免存储临时调试噪声，除非其能教授可重用的内容；
- 减少重复；
- 保留有用的细节；
- 在适当情况下创建相关概念之间的链接；
- 不要制造确定性。

<a id="documentation-workflow"></a>
## 文档工作流

在更新文档时：

- 保留正确的现有内容；
- 做出最小的有用变更；
- 优先添加而非不必要的重写；
- 确保文档描述的行为与当前实现一致；
- 将未来工作与当前功能明确分开。

<a id="failure-workflow"></a>
## 故障工作流

在纠正错误或中断的工作流时：

1. 使用具体数据重现或追踪失败；
2. 识别根本原因及受影响的调用方；
3. 在责任层应用最小修复；
4. 添加或更新针对性的回归检查；
5. 在可行时运行更广泛的关联检查和真实的冒烟测试。
